
How Playwright Sharding Works

Playwright sharding splits your test suite across multiple separate machines (runners) to run them at the exact same time.
Instead of machine A running tests 1-100, you can have 4 machines where:
• Machine 1 runs tests 1–25
• Machine 2 runs tests 26–50
• Machine 3 runs tests 51–75
• Machine 4 runs tests 76–100
Playwright manages this natively using the flag: --shard=x/y (where x is the current runner index, and y is the total number of runners).

The Complete Matrix Sharding Workflow

This GitHub Actions workflow uses a matrix strategy to create 3 parallel runners. Once all runners finish their slice of tests, a final job automatically merges all individual results into a single unified HTML report.
yaml
name: Playwright Sharded Execution
on:
  workflow_dispatch: # Allows manual execution

jobs:
  # JOB 1: Run tests in parallel shards
  run-tests:
    name: "Test Shard ${{ matrix.shard }}/3"
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false # Don't cancel other shards if one shard fails
      matrix:
        shard: [1, 2, 3] # This creates 3 parallel runner jobs
    steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with:
        node-version: lts/*
        cache: 'npm'
        
    - name: Install dependencies
      run: npm ci
      
    - name: Install Playwright Browsers
      run: npx playwright install --with-deps

    # Playwright built-in sharding logic execution
    - name: Execute Test Shard
      run: npx playwright test --shard=${{ matrix.shard }}/3
      
    # Save the special intermediate blob report (NOT the standard HTML report)
    - name: Upload Blob Report
      if: always()
      uses: actions/upload-artifact@v4
      with:
        name: all-blob-reports-shard-${{ matrix.shard }}
        path: blob-report/
        retention-days: 1

  # JOB 2: Combine all shard results into a single dashboard
  merge-reports:
    name: "Merge Shard Reports"
    needs: run-tests # Wait until all test shards finish
    if: always()     # Execute even if a test failed in the previous job
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with:
        node-version: lts/*
        cache: 'npm'
        
    - name: Install dependencies
      run: npm ci

    # Download all separate blob reports into one folder
    - name: Download all Shard Artifacts
      uses: actions/download-artifact@v4
      with:
        path: merged-blob-reports
        pattern: all-blob-reports-shard-*
        merge-multiple: true

    # Playwright stitches the blob files into a clean final HTML report
    - name: Merge Reports into HTML
      run: npx playwright merge-reports --reporter html ./merged-blob-reports

    # Upload your ultimate single test report
    - name: Upload Final HTML Report
      uses: actions/upload-artifact@v4
      with:
        name: final-playwright-html-report
        path: playwright-report/
        retention-days: 7
Use code with caution.

Step-by-Step Breakdown of the Architecture


1. Configuration Setup

To make sharding reports work seamlessly, you should add blob to the list of reporters in your local playwright.config.ts file alongside your normal reporters:
typescript
export default defineConfig({
  reporter: [
    ['html'], 
    ['blob'] // Required: Outputs lightweight result data used for merging
  ],
});
Use code with caution.

2. Parallelizing with Matrix

yaml
matrix:
  shard: [1, 2, 3]
Use code with caution.
GitHub Actions sees this array and creates 3 completely isolated, identical virtual environments to execute the steps at the exact same moment.

3. Dynamic Flag Execution

yaml
run: npx playwright test --shard=${{ matrix.shard }}/3
Use code with caution.
• Runner 1 evaluates this to: --shard=1/3 (Processes the 1st third of your spec files).
• Runner 2 evaluates this to: --shard=2/3 (Processes the 2nd third of your spec files).
• Runner 3 evaluates this to: --shard=3/3 (Processes the final third of your spec files).

4. The Report Stitching Phase

When sharding, individual runners don't know what happened on the other runners.
1. Each shard uploads a temporary .blob data file containing its isolated metrics.
2. The merge-reports job waits (needs: run-tests) for all shards to finish.
3. It downloads all .blob files into a single folder (merged-blob-reports).
4. npx playwright merge-reports unifies them into a single, cohesive HTML package containing all test results across all machines.
